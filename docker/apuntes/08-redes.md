# 08 · Redes: cómo se encuentran dos contenedores

> Anterior: [07 · Volúmenes](07-volumenes.md) · Siguiente: *(pendiente — Docker Compose)*
> Lab que lo acompaña: [labs/06-redes](../labs/06-redes/)

El apunte anterior resolvió **dónde vive el estado**. Este resuelve la otra mitad de lo que
necesita cualquier aplicación de varias piezas: **que sus piezas se encuentren**.

---

## 1. La red por defecto no resuelve nombres

Un contenedor arrancado sin decir nada de redes va a la red `bridge` de fábrica. Allí los
contenedores se alcanzan **por IP**, pero **no se resuelven por nombre**.

Y las IP que reparte Docker cambian cada vez que se recrea un contenedor. Eso las inutiliza para
lo único que uno querría hacer con ellas: escribirlas en una cadena de conexión o en un fichero
de configuración. Lo único que tienes para localizar al otro es un dato que caduca.

---

## 2. Una red propia trae DNS

Al crear una red:

```bash
docker network create labnet
```

y arrancar los contenedores con `--network labnet`, Docker levanta un **DNS interno** para esa
red: dentro de ella, **el nombre del contenedor es su nombre de host**. Un contenedor llamado
`basedatos` responde en `basedatos`, y ya.

Esto es, literalmente, lo que Docker Compose configura por ti cuando lees un
`docker-compose.yml` con `Host=basedatos` en una variable de entorno.

> **Analogía (C#).** Es **inyección de dependencias**. La aplicación no conoce la IP de la base
> de datos igual que una clase no conoce la implementación concreta: conoce un **nombre**, igual
> que conoce una **interfaz**. Docker es el contenedor de DI que resuelve ese nombre en tiempo de
> ejecución. Y el valor es el mismo: **se puede sustituir la instancia sin tocar a quien la
> usa** — se recrea el contenedor, le toca otra IP, y nadie se entera.

### El mecanismo, que se puede ver

Docker levanta un servidor DNS propio y lo **inyecta en el `/etc/resolv.conf` de
cada contenedor** que esté en una red definida por el usuario:

```bash
docker exec basedatos cat /etc/resolv.conf
```

```
➜ cloud-devops-lab git:(main) ✗ docker exec basedatos cat /etc/resolv.conf

# Generated by Docker Engine.
# This file can be edited; Docker Engine will not make further changes once it
# has been modified.

nameserver 127.0.0.11
options ndots:0

# Based on host file: '/etc/resolv.conf' (internal resolver)
# ExtServers: [host(192.168.65.7)]
# Overrides: []
# Option ndots from: internal
```

`127.0.0.11` es ese DNS embebido. Cuando el contenedor cliente pregunta por `basedatos`, se lo
pregunta a esa dirección, y Docker responde con la IP que ese contenedor tenga **en ese
momento**. Por eso el nombre es estable aunque la dirección no lo sea.

### Cómo reparte Docker las direcciones

Merece la pena saberlo porque explica un resultado desconcertante. Cada red propia recibe una
subred: la `bridge` de fábrica es la `172.17.0.0/16`, y la primera red que creas se lleva la
`172.18.0.0/16`. Dentro de ella, **Docker asigna siempre la dirección libre más baja**.

Consecuencia práctica: si borras el único contenedor de la red y lo recreas, **le vuelve a tocar
la misma IP**, porque la que tenía quedó libre. Eso obliga a montar el experimento con cuidado
si lo que se quiere demostrar es que la dirección cambia (ver el lab).

## 3. `-p` es para el mundo exterior

Publicar un puerto con `-p` abre una puerta **desde el anfitrión** hacia el contenedor. **Dentro
de la red, los contenedores se hablan por sus puertos internos sin necesidad de publicar nada.**

De ahí la práctica que conviene interiorizar pronto, porque además se pregunta en entrevista:
**una base de datos no se publica hacia fuera**. Solo se publica lo que debe ser accesible desde
fuera, que normalmente es la aplicación web. Que nadie pueda llegar al puerto de la base de datos
desde internet no es paranoia: es el mínimo.

> **Analogía.** La red propia es el **pasillo interior de una oficina**: los despachos se hablan
> sin salir a la calle. `-p` es **la puerta que da a la calle**, y solo la recepción la necesita.

En el [lab 05](../labs/05-volumenes/) la base de datos se levantó con `-p` porque el foco era
otro. En el [lab 06](../labs/06-redes/) se levanta **sin `-p`** a propósito, y el cliente llega
igual.

---

## 4. Las pruebas que lo demuestran

El lab tiene tres, y las tres son necesarias:

1. **El cliente, en otro contenedor, consulta por nombre** — con la base de datos sin publicar
   ningún puerto.
2. **El mismo comando exacto, fuera de la red, falla** al traducir el nombre. Sin esta mitad, la
   primera no demuestra nada: podría estar funcionando por cualquier otra razón.
3. **Al recrear el contenedor del servidor su IP cambia y el nombre sigue valiendo.** Esta es la
   que justifica que exista el DNS y no baste con apuntar la IP una vez.
